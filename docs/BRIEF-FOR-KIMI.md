## 你来做什么

你是这个项目的**独立架构评审人**（第二意见）。项目已有主架构师和实现者（另一个模型），你不需要写实现代码、不需要动手改文件。你要做的是：读文档、读代码，找设计漏洞、给替代方案、算账挑毛病。你出意见，用户会把意见带回给主架构师裁决。

## 项目背景（30 秒版）

- **目标**：给用户的私人 DeepSeek 账号做「有记忆」的个人助理 + 拉进一个 QQ 三人小群陪聊
- **核心诉求**：记忆真实有效（写→存→取→注入全链路闭环）+ token 开销受控 + 自建可维护（TypeScript strict / Node ≥24 / 单进程）
- **现状**：P0（CLI 对话闭环 + L0 原文库）与 P1（facts 指数衰减记忆 / selfNote / bigram 检索 / 触发式召回 / 闲置压缩）已完成并通过评审；P2（QQ 脑侧）进行中；`qq-gateway` 将作为独立仓库实现 QQ 传输
- **技术选型（已定，别建议推翻）**：DeepSeek 官方 API 为主、DSH 桌面端兜底；本地语义检索（Qwen3-Embedding-0.6B）是 P3 既定路线、只审参数不审存废；运行时依赖 ≤ 5
- 唯一第三方：SnowLuma（QQ 协议的 OneBot 网关，受 EULA 约束只探测不代启）

## 重点审什么（我们最想要的第二意见，按此清单逐条回应）

**A. ADR 挑刺**——对以下决策提反对意见或补强证据：

- D1：TypeScript 而非 Rust（理由是 vibecoding 效率与风险面无关）
- D3：检索「触发式」而非每轮；embedding 槽位与 bigram 起步
- D5：艾宾浩斯参数——半衰期 45 天、`h = h0 × (1 + 0.5 × min(reviews, 8))`、自动复习钩子（gram 重叠 ≥ 0.5）、注入双预算 30 条/900 字
- D6：事实「只归档不删除」，矛盾事实并存不相互压制
- 前缀缓存纪律：system 三段式（静态/会话准静态/动态尾部）
- D7：QQ 拆成独立仓库独立进程；CONTRACT v1 的完整性——失败语义（脑挂/网关挂）、限流归属（网关 429、脑重试 2 次）、字段演进规则有没有漏洞

**B. 三个悬而未决的问题**（给「方案 + 权衡」两组以上的选项，不要只挑刺）：

1. **检索漏检**：v1 触发只有回忆词正则（记得/上次/说过…），P3 的语义检索还没上线。在「日常闲聊零检索开销」的前提下，怎么低成本提高该检索时的召回率？
2. **矛盾记忆**：「只归档不删除」与「纠正错误事实」怎么平衡？新旧并存现在会导致旧事实继续注入——要不要引入"新事实压制旧事实"（降权而非删除）？
3. **静态段切分**：P2 之后是多会话 + DeepSeek 官方 API 的上下文缓存。persona / facts / summary / selfNote 各放在三段里的哪一段，缓存命中率最优？当前做法（全塞静态段、facts 变才重建）有什么隐患？

**C. token 经济再审计**——对着 README 的配置默认值逐项挑毛病，特别是：

- 合批窗口 2 秒：QQ 群消息爆发时会不会叠出超预算的唤醒包
- 群聊与私聊的注入预算要不要分开（现在共用 900 字 facts 预算）
- 触发式检索命中率与「检索一次的成本」的临界点在哪（给出你的估算口径）

## 护栏：这个项目的规模红线（防止过度设计）

在给任何建议前先对照这几条，越线就注明「长期选项」：

- 单用户 + 一个三人小群，消息量千级（不是十万级），单机单进程
- 运行时依赖 ≤ 5，任何建议让依赖 +1 的，必须同时给出「不带它的替代方案」
- 不要建议：数据库、消息队列、微服务、agent 框架、多智能体编排、容器化
- 不要建议「重写」；已通过的 P0/P1 只接受小修意见
- 地图炮式的泛泛而谈（"建议加强可观测性""考虑引入 LLM 网关"）不要写
