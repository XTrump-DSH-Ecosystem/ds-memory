## 0. 目标与边界

在 P3-0 同一评测口径下，评估两个 embedding 后端候选（Ollama 边车 / ONNX Runtime 进程内）是否值得替换当前 `BigramRetriever`，并给出可执行实验步骤、授权点与决策矩阵。

**边界**
- ds-memory 保持单进程。若候选引入外部 sidecar，必须单列运维与故障代价。
- 本方案不改生产检索参数、不改 `Retriever` 接口、不实现 `EmbeddingRetriever`。
- 未实测前不宣布选型；所有门槛与倾向均为“提议、待批准”。

## 1. 候选

| 编号 | 方案 | 运行形态 | 新 npm 依赖 | 说明 |
| --- | --- | --- | --- | --- |
| A | Ollama + Qwen3-Embedding-0.6B | localhost HTTP sidecar（`127.0.0.1:11434`，内置 `fetch` 调用 `/api/embed`） | 无 | 边车独立进程；可复用 GPU/CPU 后端 |
| B | ONNX Runtime + Qwen3-Embedding-0.6B | 进程内 native 推理 | 有（`onnxruntime-node` 等） | 单进程内嵌；引入 native 依赖 |
| C | bge-small-zh-v1.5 | 仅当 A/B 超预算时评估 | 视后端 | 384 维、更小体积的降级候选 |

模型体积/维度参考（README 预估值，实测为准）：Qwen3-Embedding-0.6B ≈ 1024 维、约 1.2GB；bge-small-zh-v1.5 ≈ 512 维、约 100MB。

## 2. 评测口径（与 P3-0 完全一致）

- 数据集：`tests/eval/cases.json`（50 case / 23 corpus，全合成脱敏）；同一 runner 逻辑，仅把 `BigramRetriever` 的检索实现替换为候选 embedding 后端（实验探针，不落生产代码）。
- 指标：`Recall@5`、`MRR`、检索隔离负例正确率、应不命中负例正确率。
- 向量口径：按模型卡固定 query instruction / document 前缀；向量 L2 归一化后计算余弦；模型版本、量化格式、维度与文件哈希必须记录，A/B 不得使用不同口径。
- 本地边界：全部推理仅在本机；消息正文不得发往任何外部服务。Ollama 仅访问 `127.0.0.1`，端口从配置/探测获得，不假设固定 `11434`。
- 新增资源/性能指标（P3-0 未测，P3-1 补齐）：
  - 冷启动：进程/边车首次可用时间（含模型加载与索引构建）；
  - 热查询 p50/p95（单 query embedding + 相似度检索）；
  - RSS 增量（进程内或“进程 + sidecar”合计）；
  - 安装体积增量（模型 + 运行时）；
  - Windows 兼容（Node 24 / 路径 / 杀软 / GPU 可用性）；
  - 故障模式与降级路径；
  - 依赖增量（npm 依赖数与 native 依赖）。

## 3. 主审修订后的门槛（首轮实测后可调整一次）

> 目标值用于判断是否值得进入 P3-2；硬门槛不通过则不得替换 bigram。不得为凑分数修改生产检索参数。

- 质量硬门槛：
  - `Recall@5` ≥ 0.93，且相对 P3-0 基线绝对提升 ≥ 0.05；目标值 ≥ 0.95。
  - `MRR` ≥ 0.90，且不得低于基线 0.8650；目标值 ≥ 0.93。
  - 检索隔离与应不命中负例正确率必须保持 1.000。
- 性能/资源门槛：
  - 热查询 p50 ≤ 150ms、p95 ≤ 500ms；目标值 p50 ≤ 80ms、p95 ≤ 250ms（含 embedding 与相似度计算）。
  - 冷启动：候选 A ≤ 60s（Ollama 已安装、模型已拉取）；候选 B 模型加载 + 索引构建 ≤ 45s。
  - 内存：候选 A 为“ds-memory + Ollama”合计增量 ≤ 2.5GB；候选 B 单进程 RSS 增量 ≤ 2GB。
  - 安装体积增量 ≤ 2.5GB；超过则触发候选 C（bge-small-zh-v1.5）评估。
- 失败降级：embedding 不可用时自动降级 `BigramRetriever`，不得阻断聊天或 L0 写入；连续失败告警，不做无界重试。

## 4. 候选代价与风险

### 4.1 A · Ollama sidecar

- 单进程约束被打破：需单独管理 Ollama 的安装、启动、升级、端口与自启。
- Ollama 由用户管理，ds-memory 不代启动/停止，只探测和调用；端口冲突时失败降级，不自动改端口、不自动拉起边车。
- 故障面：Ollama 未启动/崩溃/端口冲突/模型未拉取/网络失败 → 全部 embedding 请求失败；需降级与告警。
- 运维代价：Windows 下常驻后台、开机启动、GPU 驱动与 CUDA/ROCm 环境、模型存储与更新。
- 优势：ds-memory 零 npm 依赖增量；embedding 与聊天推理可在 GPU 上卸载 CPU；故障隔离在边车。

### 4.2 B · ONNX Runtime 进程内

- 引入 `onnxruntime-node` native 依赖；Node 24 ABI/预编译二进制与 Windows 平台兼容需实测（长路径、杀软、x64）。
- 单进程内内存与冷启动：模型常驻内存，RSS 增量显著；首加载延迟。
- 故障面：native 加载失败/OOM/模型文件缺失/量化格式不兼容。
- 优势：不引入第二进程，部署与生命周期更简单。

## 5. 实验步骤

1. 无下载可行性检查：确认 Ollama 是否已安装、磁盘/内存/GPU、`11434` 占用与 Windows 版本；不通过则先报预算，不下载。
2. 用户授权：模型下载、Ollama 安装、`npm install`（候选 B 新增依赖）与相关网络访问；未获书面授权前不执行。
3. 环境准备：候选 A 安装并启动 Ollama、拉取 Qwen3-Embedding-0.6B；候选 B 安装 ONNX 运行时并准备同模型 ONNX 导出/量化文件。
4. 探针：写独立实验脚本（非生产 `EmbeddingRetriever`），复用 `tests/eval/cases.json`，分别跑 A/B，输出 P3-0 全口径指标与新增资源指标。
5. 记录：每候选 3 次以上热查询采样，取 p50/p95；冷启动单独计时；用进程/任务管理器采集 RSS；记录安装体积。
6. 决策矩阵填表（见 §6），给出推荐倾向。
7. 把实测结论提交批准；批准前不实现、不改 `src/`。
